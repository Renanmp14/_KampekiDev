Por que este servidor existe

O app desktop (Electron) não abre no Mac da cliente: o XProtect, antivírus do próprio macOS, classifica aplicativos não assinados como malware e os move para o Lixo — e não oferece a opção "Abrir Mesmo Assim". Resolver exigiria a notarização da Apple (US$ 99/ano). Como o Kampeki já é uma aplicação web por dentro, escolhemos hospedá-la: o Mac abre uma URL no navegador e o problema deixa de existir. O Windows continua no app desktop, com auto-update funcionando.

Duas consequências importantes desse desenho

1. O Node escuta apenas em 127.0.0.1:3001 — ou seja, só o Caddy, de dentro da própria máquina, consegue falar com ele. A internet nunca alcança o Node diretamente. Isso é intencional e mais seguro do que expor a porta 3001.

2. A VM não guarda dados. Tudo mora no Google Sheets. Se o servidor for destruído, nenhum lançamento se perde — você recria a VM com este manual e volta ao ar. O que existe de insubstituível na VM é apenas o .env (e você tem a chave original no Google Cloud).

1. Conta e região Oracle

Cadastro em oracle.com/br/cloud/free. O cartão de crédito serve apenas para verificação de identidade — o Always Free não gera cobrança (há uma cobrança-teste de ~US$ 1 que é estornada).

A região é definitiva

A região escolhida no cadastro é a home region e não pode ser trocada depois. Os recursos Always Free existem somente nela. A nossa é Brazil East (São Paulo). Se um dia você criar recursos e não os encontrar, confira o seletor de região no canto superior direito da console.

2. A chave SSH

Servidores Linux na nuvem não usam senha para acesso — usam um par de chaves. A pública fica no servidor; a privada fica no seu PC e funciona como a fechadura correspondente. Ninguém entra sem ela.

gerar o par (feito uma vez, já está pronto)
ssh-keygen -t ed25519 -C "kampeki-oracle" -f "$env:USERPROFILE\.ssh\kampeki_oracle"

Isso criou dois arquivos em C:\Users\Renan Milech Pereira\.ssh\:

  • kampeki_oracle — a privada. Nunca sai do seu PC.
  • kampeki_oracle.pub — a pública. Foi colada na Oracle ao criar a VM.
ver a chave pública (para colar em algum lugar)
Get-Content "$env:USERPROFILE\.ssh\kampeki_oracle.pub" | Set-Clipboard

Usar o servidor de outro computador

Copie o arquivo kampeki_oracle (o privado) para a pasta .ssh do outro computador. No Linux/macOS é preciso ajustar a permissão, senão o SSH recusa a chave:

no Linux/macOS, depois de copiar
chmod 600 ~/.ssh/kampeki_oracle

3. A rede (VCN)

Uma VCN (Virtual Cloud Network) é a rede privada onde a VM vive. Ela precisa de uma subnet pública e de um Internet Gateway para que a máquina seja alcançável de fora.

Não crie a rede pelo formulário da instância

Tentamos primeiro criar a VCN dentro da tela "Create instance" e o botão "Automatically assign public IPv4 address" ficava permanentemente desabilitado, com o aviso "You must select a public subnet". O formulário da instância não cria o Internet Gateway, então a subnet nunca é considerada pública de fato. Crie a rede antes, pelo assistente de Networking.

O caminho que funciona

  1. ☰ Menu → Networking → Virtual cloud networks
  2. Botão Start VCN wizard → escolher "Create VCN with Internet Connectivity"
  3. Nome vcn-kampeki, compartment renanmp (root), e todos os CIDRs no padrão (10.0.0.0/16 para a VCN, 10.0.0.0/24 para a subnet pública)
  4. Enable IPv6: deixar desmarcado — não usamos, e marcar só criaria uma segunda pilha de rede para configurar
  5. Create. Em ~1 minuto ele monta a VCN completa: subnet pública, subnet privada, Internet Gateway, NAT Gateway e tabelas de rota.

5. O firewall duplo

O erro nº 1 de quem começa na Oracle — e nós caímos nele

Existem dois firewalls independentes, e liberar uma porta em apenas um deles não adianta nada. Passamos por isso: liberamos as portas dentro do Ubuntu, o Caddy tentou emitir o certificado e o Let's Encrypt respondeu "Timeout during connect (likely firewall problem)" — porque faltava a liberação no painel.

A regra da porta 22 (SSH) já vem criada pelo wizard da VCN.

Por que a porta 80 é obrigatória mesmo o site sendo HTTPS

O Let's Encrypt valida que você controla o domínio buscando um arquivo em http://kampeki.duckdns.org/.well-known/acme-challenge/… — pela porta 80. Sem ela, o certificado nunca é emitido. Depois disso, a porta 80 ainda serve para redirecionar quem digitar http:// para a versão segura.

Erros comuns de conexão

Permission denied (publickey) → caminho da chave errado (não use o .pub) ou usuário errado (é ubuntu, não opc nem root).
Connection timed out → a VM está desligada, o IP mudou, ou a regra da porta 22 sumiu da Security List.

7. Preparar o servidor

7.1 Swap — obrigatório nesta VM

Com 1 GB de RAM, qualquer operação mais pesada (um npm install grande, um build) mata o processo com "JavaScript heap out of memory". O swap é uma extensão da memória em disco: mais lento, mas evita o travamento.

criar 2 GB de swap permanente
sudo fallocate -l 2G /swapfile
sudo chmod 600 /swapfile
sudo mkswap /swapfile
sudo swapon /swapfile
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab

A última linha grava no /etc/fstab, que é o que faz o swap voltar depois de um reboot. Conferir com free -h.

7.2 Node.js, git e pm2

instalar
sudo apt update
sudo apt install -y git curl ca-certificates
curl -fsSL https://deb.nodesource.com/setup_22.x | sudo -E bash -
sudo apt install -y nodejs
sudo npm install -g pm2

O Node vem do repositório NodeSource, não do apt padrão do Ubuntu — o do apt costuma estar muitas versões atrasado. Conferir: node -v, npm -v, pm2 -v.

O que é o pm2

Se você rodasse node src/app.js e fechasse o SSH, o app morreria junto. O pm2 é um gerenciador de processos: mantém o app rodando em segundo plano, religa automaticamente se ele travar, guarda os logs e volta sozinho quando a VM reinicia.

A regra que mais quebra o .env

O GOOGLE_CREDENTIALS_JSON tem que ficar em uma única linha. Os \n dentro da private_key são literais (dois caracteres: barra e "n") e devem permanecer assim — se virarem quebras de linha reais ao colar, o arquivo quebra e o app não sobe. No nosso deploy, o .env ficou com 13 linhas e 2.664 bytes; se o seu tiver dezenas de linhas, o JSON foi quebrado.

Como o .env foi enviado (sem passar por arquivo no disco)

Um script leu o JSON da Service Account, serializou em uma linha, gerou senha e JWT aleatórios, e o resultado foi canalizado direto para dentro do servidor — sem nunca criar um arquivo com segredos no seu Windows:

o padrão do envio

  "cat > ~/_KampekiDev/KampekiDash/backend/.env && chmod 600 ~/_KampekiDev/KampekiDash/backend/.env"

O chmod 600 deixa o arquivo legível apenas pelo dono (ubuntu). Ver Mexer no .env para alterar qualquer valor depois.

10. Subir o app com pm2

iniciar (o comando exato usado)
cd ~/_KampekiDev/KampekiDash/backend
pm2 start npm --name kampeki -- start
Atenção: NÃO use pm2 start src/app.js

Foi a primeira coisa que tentamos e não funciona neste projeto. O pm2 mostrava o processo como online, consumindo 123 MB, mas sem nenhum log e com a porta 3001 fechada. A causa está no fim do backend/src/app.js: 

const invokedDirectly = process.argv[1]
  && pathToFileURL(process.argv[1]).href === import.meta.url;
if (invokedDirectly) startServer();

Esse guarda existe para o Electron poder importar o startServer sem subir um servidor duplicado. Só que o pm2, em modo fork, importa o script a partir do wrapper dele (ProcessContainerFork.js). Assim process.argv[1] aponta para o wrapper, a comparação dá false e startServer() nunca é chamado — o módulo carrega e o processo fica vivo sem fazer nada.

Mandando o pm2 executar npm start, quem roda o script é o node de verdade, process.argv[1] volta a ser o app.js e o servidor sobe normalmente. Isso vale para qualquer gerenciador de processos que importe o módulo em vez de executá-lo.

Fazer o pm2 voltar sozinho depois de um reboot

registrar no systemd
pm2 save
sudo env PATH=$PATH pm2 startup systemd -u ubuntu --hp /home/ubuntu
pm2 save

O pm2 save congela a lista de processos atual; o pm2 startup cria o serviço pm2-ubuntu no systemd. Ambos estão habilitados nesta instalação, junto com o caddy — se a VM reiniciar, tudo volta sem intervenção.

11. Frontend — onde buildar e como enviar

Não existe "servidor de frontend" separado

O backend/src/app.js detecta a pasta frontend/dist e, se ela existir, serve os arquivos do React na mesma origem das rotas /api. Qualquer URL que não comece com /api devolve o index.html, para o React Router resolver a rota no navegador. É por isso que o app funciona com um único processo e sem configuração extra de CORS.

O build é feito no seu Windows e enviado pronto. Dois motivos: a VM de 1 GB sofre com o vite build, e assim você testa localmente exatamente o que vai para o ar.

1) buildar
cd "$env:USERPROFILE\Documents\_KampekiDev\KampekiDash\frontend"
npm run build

Gera a pasta dist/ (~3,8 MB). O aviso "Some chunks are larger than 500 kB" é conhecido e inofensivo.

2) enviar para o servidor
scp -i "$env:USERPROFILE\.ssh\kampeki_oracle" -r dist ubuntu@163.176.35.169:/home/ubuntu/_KampekiDev/KampekiDash/frontend/
Detalhe do scp que confunde

O destino termina em /frontend/, não em /frontend/dist. O scp -r dist destino/ cria destino/dist. Se você apontar para /frontend/dist, vai acabar com dist/dist e o site não carrega.

Depois de trocar o dist, não é obrigatório reiniciar o app (o Express lê os arquivos do disco a cada requisição), mas reiniciar é inofensivo e garante estado limpo.

12. O endereço (DuckDNS)

Certificados HTTPS não são emitidos para endereços IP — é preciso um nome. O DuckDNS fornece subdomínios gratuitos, sem cartão e sem prazo.

  1. Entrar em duckdns.org com a conta Google
  2. Criar o domínio kampeki → vira kampeki.duckdns.org
  3. Preencher o campo current ip com 163.176.35.169 → update ip
  4. Guardar o token exibido no topo da página (serve para atualizar o IP por script)
conferir se o nome está apontando certo
nslookup kampeki.duckdns.org

Quer um domínio próprio depois? Compre em qualquer registrador (~R$ 40–60/ano), crie um registro A apontando para o IP da VM, e troque o nome no Caddyfile. O Caddy emite o novo certificado sozinho. É uma linha de mudança.

13. Caddy e HTTPS

O Caddy é o servidor que fica na frente. Ele recebe as visitas em 443, resolve o certificado com o Let's Encrypt (emissão e renovação automáticas) e repassa tudo para o Node na porta local 3001.

instalação (repositório oficial)
sudo apt install -y debian-keyring debian-archive-keyring apt-transport-https curl
curl -1sLf 'https://dl.cloudsmith.io/public/caddy/stable/gpg.key' | sudo gpg --dearmor -o /usr/share/keyrings/caddy-stable-archive-keyring.gpg
curl -1sLf 'https://dl.cloudsmith.io/public/caddy/stable/debian.deb.txt' | sudo tee /etc/apt/sources.list.d/caddy-stable.list
sudo apt update
sudo apt install -y caddy

A configuração inteira

O arquivo /etc/caddy/Caddyfile tem exatamente três linhas:

kampeki.duckdns.org {
    reverse_proxy 127.0.0.1:3001
}

Isso sozinho já entrega: certificado válido, renovação automática, redirecionamento de http:// para https:// (HTTP 308) e compressão.

editar e aplicar
sudo nano /etc/caddy/Caddyfile
sudo caddy validate --config /etc/caddy/Caddyfile
sudo systemctl restart caddy

No nano: Ctrl+O Enter salva, Ctrl+X sai. Rode sempre o validate antes do restart.

acompanhar a emissão do certificado
sudo journalctl -u caddy -n 30 --no-pager

A linha que confirma sucesso é certificate obtained successfully.

Se o IP mudar

O IP público desta VM é efêmero

Por padrão, a Oracle atribui um IP efêmero: ele permanece o mesmo enquanto a instância estiver rodando, mas pode mudar se você parar (Stop) e iniciar (Start) a máquina. Um simples sudo reboot de dentro do sistema não muda o IP — o risco está em parar a instância pelo painel.

Solução A — tornar o IP permanente (recomendado)

  1. Página da instância → seção Primary VNIC → em IPv4 Addresses, os três pontinhos → Edit
  2. Em Public IP Type, trocar de Ephemeral para Reserved
  3. Dar um nome (ex.: ip-kampeki) e salvar

IPs reservados também entram no Always Free (1 gratuito por conta enquanto estiver em uso).

Solução B — atualizar o DuckDNS quando mudar

Se o IP mudar, o site fica inacessível até o DNS ser corrigido. Manualmente, é entrar no duckdns.org e atualizar o campo current ip. Para automatizar, com o seu token:

agendar atualização automática a cada 5 minutos
(crontab -l 2>/dev/null; echo "*/5 * * * * curl -s 'https://www.duckdns.org/update?domains=kampeki&token=SEU_TOKEN&ip=' >/dev/null") | crontab -

Deixando o parâmetro ip= vazio, o DuckDNS usa automaticamente o IP de onde a requisição partiu — ou seja, o da própria VM. Troque SEU_TOKEN pelo token da sua conta.

Problemas que enfrentamos e como resolver

Todos os itens abaixo aconteceram de verdade durante este deploy.

1. O botão de IP público fica desabilitado ao criar a instância

Sintoma: "You must select a public subnet to assign a public IPv4 address", e o toggle não liga de jeito nenhum.

Causa: a VCN estava sendo criada dentro do formulário da instância, que não cria o Internet Gateway — sem ele, nenhuma subnet é realmente pública.

Solução: criar a rede antes pelo Start VCN wizard (opção Create VCN with Internet Connectivity) e, na instância, apenas selecionar a VCN e a subnet pública. Ver seção 3.

2. "Out of capacity" ao criar a VM ARM

Causa: o shape gratuito ARM vive esgotado em São Paulo, que tem um único Availability Domain — a dica da Oracle de "tente outro AD" não se aplica.

Solução: usar o AMD E2.1.Micro. Ou tentar o ARM com 1 OCPU / 6 GB, em horários alternados. Ver seção 4.

3. O site não responde, mas o SSH funciona

Sintoma: a porta 22 conecta e as portas 80/443 dão timeout. O Caddy falha com "Timeout during connect (likely firewall problem)".

Causa: as regras de entrada faltavam na Security List do painel (só tinham sido criadas dentro do Ubuntu).

como diagnosticar
Test-NetConnection -ComputerName 163.176.35.169 -Port 80

Se der False aqui mas o iptables da VM estiver liberado, o problema é a Security List. Ver seção 5.

4. O pm2 diz "online" mas o site não abre

Sintoma: pm2 status mostra online, mas os logs estão vazios e curl http://127.0.0.1:3001/api/health não responde.

Causa: o app foi iniciado com pm2 start src/app.js, e o guarda invokedDirectly impede o startServer() de rodar quando o script é importado.

solução
pm2 delete kampeki
cd ~/_KampekiDev/KampekiDash/backend
pm2 start npm --name kampeki -- start
pm2 save

Explicação completa na seção 10.

5. O app sobe mas não lê a planilha

Sintoma nos logs: [initSheets] Falha ao inicializar a planilha.

Causas prováveis, em ordem:

  1. O GOOGLE_CREDENTIALS_JSON quebrou em várias linhas (conte as linhas: devem ser 13)
  2. A chave foi apagada ou desativada no Google Cloud
  3. A planilha não está compartilhada com kampeki-app@kampeki-finance.iam.gserviceaccount.com
  4. O GOOGLE_SHEET_ID está errado

Quando isso ocorre, o app ainda assim sobe (por decisão de projeto, o erro é registrado e o servidor continua), mas as telas ficam vazias.

6. Como investigar qualquer travamento na inicialização

Rodar o app em primeiro plano contorna o pm2 e mostra tudo na tela — foi assim que descobrimos o problema nº 4:

pm2 stop kampeki
cd ~/_KampekiDev/KampekiDash/backend
timeout 45 node src/app.js
pm2 start kampeki

7. O certificado HTTPS não é emitido

Verifique, nesta ordem: a porta 80 está aberta nos dois firewalls? O DNS aponta para o IP certo (nslookup)? O Caddy está rodando?

ver o motivo exato da falha
sudo journalctl -u caddy -n 40 --no-pager | grep -i error
Não fique tentando repetidamente

O Let's Encrypt tem limite de tentativas com falha (cerca de 5 por hora por domínio). Se estourar, você fica bloqueado por uma hora mesmo depois de corrigir o problema. Diagnostique primeiro, reinicie o Caddy depois.

8. O site abre mas mostra a versão antiga

Cache do navegador. Ctrl+F5 (ou Cmd+Shift+R no Mac). Se persistir, confira se o scp do dist foi mesmo para a pasta certa (ver seção 11).

O endpoint POST /api/auth/login aceita tentativas ilimitadas. No app desktop isso era aceitável (só rodava na máquina do usuário); na web, não é — qualquer um pode tentar senhas em série. É uma mudança de código no backend, ainda não aplicada.
